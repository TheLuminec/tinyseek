# tinyseek

Synthetic-data distillation of prompt-specific object detectors for the ESP32-S3.

Goal: given a text prompt (e.g. "cup", "backpack"), train a tiny detector that runs on an ESP32-S3 camera board and outputs bounding boxes, using Stable Diffusion images labeled by an open-vocabulary teacher instead of manually labeled data.

Owner: Caleb Turner (solo). Started as a CSE 534 (graduate Generative AI, Miami University) final project, but the repo is a standalone project and should read that way: no course-specific naming in code, comments, or docs.

## Pipeline

1. **Generate**: Stable Diffusion via Hugging Face Diffusers, with a LoRA/QLoRA adapter fine-tuned on a few hundred ESP32-camera-style images to close the domain gap (low resolution, sensor noise).
2. **Label**: an open-vocabulary teacher (Grounding DINO or OWL-ViT) converts each prompt into bounding boxes; filter by a confidence threshold.
3. **Distill**: train a MobileNet-class student detector, quantize to int8, deploy to the ESP32-S3 (ESP-DL or TFLite Micro). Keep a laptop-hosted copy of the student as a fallback and for evaluation.
4. **Evaluate** four training conditions: real only, teacher-labeled real, synthetic only, synthetic plus real. Also sweep the number of synthetic images.

## Datasets

- MS COCO: real training images and the held-out evaluation set for 2-3 target prompts that map to COCO categories.
- Synthetic set: roughly 2,000-5,000 generated images per prompt, auto-labeled by the teacher.
- ESP32-S3 camera test set: roughly 200 self-collected photos from the target hardware, used to measure the real deployment domain.

## Metrics

- mAP@0.5
- Expected calibration error (ECE) of detection confidences
- CLIP semantic similarity between the prompt and detected crops
- FID/KID for realism of synthetic images (if time allows)
- Model size and on-device latency

## Expected outputs

- Results table: four training conditions x (mAP, ECE, model size, latency)
- Data-efficiency curve: mAP vs. number of synthetic images
- Gallery of synthetic images, plus success and failure cases from the real camera
- Live demo: ESP32-S3 drawing bounding boxes for a typed prompt
- Stretch goal: detector boxes drive a pan-tilt Nerf turret so it aims at the prompted object

## Constraints to design around

- ESP32-S3 has roughly 8 MB PSRAM; expect 96-160 px inputs and a MobileNet-class or FOMO-style model. Check memory and latency budgets before committing to an architecture.
- Training and generation run on a GPU machine or the OSC cluster (SLURM batch jobs); the board only runs inference. Keep training scripts runnable both interactively and as SLURM jobs, with paths and hyperparameters in config files rather than hardcoded.
- Experiments must be reproducible: fix seeds, log configs, and record which synthetic set and teacher threshold produced each result.

## Working conventions

- Python for everything off-board (PyTorch, Hugging Face Diffusers/Transformers); C/C++ for firmware. Use type hints and keep functions small and testable.
- Never commit datasets, model checkpoints, generated images, or secrets (API tokens, Wi-Fi credentials). Keep them gitignored and document how to regenerate them.
- Before running anything long (generation, training, SLURM submission), state what will run, the expected duration, and the output location, and prefer a small smoke test first.
- When changing the student architecture, input size, or quantization settings, re-check that the model still fits on the ESP32-S3 before running full experiments.
- Report results with the exact config and seed used. Do not report numbers that were not produced by a run in this repo.
- Keep commits focused, with messages saying what changed and why.

## Long-running work: Avalon Monitor (`avm`)

Anything that runs longer than about a minute (dataset downloads, SD generation, teacher labeling, training, quantization) is tracked with `avm` (`~/.local/bin/avm`) so it shows on the Avalon Monitor dashboard. `avm --help` has the details.

- Run `avm task list --status running` before launching, so nothing is started twice.
- Wrap the command: `avm run "tinyseek <what> <prompt/condition>" -- <command>`. Names always start with "tinyseek" and say what runs, e.g. `avm run "tinyseek train cup synth_only seed1" -- python -m tinyseek.train.train ...`.
- GPU jobs declare the GPU: `--gpu`, plus `--exclusive --wait` for heavy jobs (training, generation, teacher labeling over full sets) so they queue behind other heavy jobs instead of colliding. Add `--vram <N>G` when the need is known (SD generation peaks near 10 GB).
- Multi-step work that is not one command: `avm task start "<name>" --expect <secs>`, then `avm task beat <id> --progress <0-1>`, then `avm task done <id>` or `avm task fail <id> --rc <n> --note "<why>"`. Long generation runs one avm task per prompt so the dashboard shows progress.
- The 1080 Ti on AVALON is shared. Before any job that holds the GPU for hours (e.g. the ~4 h synthetic-set generation), message the System Coordinator session with the command and expected duration and wait for the slot.

## Decisions

- Target prompts: person (COCO 1), cup (47), backpack (27).
- Student: CenterNet-style box detector, MobileNetV2-0.5 backbone (narrowest timm width with pretrained weights), single stride-8 head, 128x128 input. Chosen over FOMO so standard mAP@0.5 applies.
- Runtime: ESP-DL (export via esp-ppq, target esp32s3). Any layer that breaks ESP-DL's power-of-two exponent rule is moved to int16 automatically by the exporter.
- Board: Freenove ESP32-S3 (N16R8, OV2640) planned; keep firmware board-configurable.
- Camera lens: 160-degree wide-angle (fisheye-type) OV2640 module on a 75 mm flex, per the user's purchase listing. Objects look small and barrel-distorted, so a 128 px input loses detail fast; consider a center crop of a higher-resolution frame and distortion augmentation for synthetic images. Camera rig: tilt at most 30 degrees down for training photos, or the rig's tray edge enters the frame.
- Camera capture settings are frozen for data collection as of 2026-11-06 (`firmware/capture`, logged in each `session.txt`): SVGA JPEG q10, VFLIP/HMIRROR off (rig v1), AWB auto, AE level 0, aec2 off, 4x gain ceiling, 4 s warmup. The detector firmware must use the same sensor settings. Photos from the first (faulty, green) OV2640 module or from the washed-out 16x/AE+1 settings are not usable.
- Synthetic-data findings (2026-11-10, backpack, synthetic-only detectors, 1,000 images, 3 seeds, scored on the reviewed ESP32 photos): images from the domain LoRA reach AP@0.5 0.128, while plain SD, plain SD + analytic camera simulation (tinyseek.generate.camsim), and LoRA img2img stylizing all score ~0.00. The camera *look* alone does not transfer; what helps is the scene/object content the LoRA learned, from the same photos used as the test set. Treat ESP32-test gains from LoRA images as possibly leaked until measured on photos the LoRA never saw (hold out sessions from LoRA training). Summary: runs/summary_stylize_sweep.json.
- Held-out check (2026-11-11, DESKTOP-C, configs/heldout_013_014.yaml and lora_v2_holdout_013_014.yaml; backpack, synthetic-only, 1,000 fp16 images, raw labels at 0.3, seeds 0-2), AP@0.5 on the 227 photos of sessions 013/014: LoRA v2, which saw them, 0.236; a LoRA trained without them 0.043; plain SD 0.006. Most of the earlier LoRA gain on camera photos was leakage; a small real transfer remains (held-out LoRA > plain SD on every seed). Any generator or LoRA comparison must be scored on sessions its LoRA never saw.
- Larger local generator (2026-11-13, AVALON, scripts/heldout_qwen.sh, set qwen21_turbo_v2): 1,000 backpack images from Qwen Image 2.1 Turbo through a ComfyUI server (tinyseek.generate.comfy, configs/generate_comfy.yaml; 8 steps, 768x576, ~26 s per image on the 1080 Ti, research/non-commercial licence), prompted with sampled scene descriptions and no camera LoRA. OWLv2 found a backpack in 992 of 1,000. Synthetic-only detectors, raw labels at 0.3, seeds 0-2, AP@0.5 on sessions 013/014: 0.142 (0.139-0.147), against 0.043 for the held-out SD LoRA and 0.006 for plain SD. The same images through camsim (preset "camera") score 0.024: the simulator magnifies the frame centre, pushes edge objects out of view and darkens heavily, so as built it hurts. Scene content from a stronger generator is what transfers so far; Qwen got much longer prompts than SD 1.5, so generator and prompt detail are not separated. Summary: runs/summary_heldout_qwen21_turbo_v2.json. Reloading models between images is not the generation cost (one job of 8 prompts: 61.9 s per image vs 62.0 s singly at 1184x896); frame size is.
- SD 1.5 generation runs in fp32 with LCM-LoRA (few steps) because Pascal GPUs have no fast fp16.
- The reported model is the final-epoch checkpoint; COCO val2017 is the test set and is never used to select checkpoints.
